# PharmDesk v0.4.7 — P0: аудит кода и оценка готовности к локальной валидации

Дата: 22.11.2026. Аудит на основе ветки `feature/v047-matching-quality` (коммит `ed7a643c`).
**Статус:** исправления для предварительных испытаний размещены в дочерней ветке `feature/v047-validation-safety`.
Рабочая база и ветка `main` не менялись.

## Подтверждённые недостатки и решения

1. **Разные правила извлечения торгового названия (важно).**
   В массовом анализе применялся `_resolve_trade` со словарём ГРЛС, а в `source_candidates` — отдельный `trade_name_from_stock`, обрезавший название по первой цифре/форме.
   Исправление: общая функция `resolve_stock_trade_name`; числовые и составные названия не превращаются в совпадение по префиксу.
2. **Неизолированное подключение к базе (критично для испытаний).**
   `app.database` получает `DATABASE_URL` при импорте. Если запустить 0.4.7 в старой папке, можно непреднамеренно записать новые `matching_runs` в рабочую SQLite.
   Решение: испытания только в другом git clone, тестовая SQLite — вне рабочего проекта, фактический URL перепроверяется до и после импорта. Тестовая программа не поднимает сервер и не пишет в рабочий репозиторий.
3. **Неполная оценка сверх 2000 строк (ограничение).**
   Если точных строк по торговому названию более 2000, анализируются первые 2000 по ID; лучшая запись может оказаться за ограничением. Программа уже помечает результат как неполный. Это блокирующее ограничение для интерпретации таких товаров, но не ошибка сохранности данных.
4. **Поле «Формы выпуска» многовариантно (медицинский риск).**
   Один текст может описывать несколько форм и доз. Версия 0.4.7 избегает автоматического позитивного совпадения при нескольких дозировках, однако полноценное извлечение однозначных связанных пар форма–доза пока не реализовано. Не включать в «подтверждённые» по результатам машинного сравнения.
5. **Множественные регистрационные строки и категории (ограничение).**
   Итоговый «сильный кандидат» по-прежнему требует одну запись по названию. Это осознанная консервативная политика, а не показатель точности. Количество сильных кандидатов нельзя использовать как единственный KPI.
6. **Агрегаты старого анализа (ограничение).**
   В старом запуске сохранялись только первые 30 строк; новый аудит не должен выдавать их за весь набор. Код 0.4.7 учитывает `evidence_scope`.
7. **История и физическая целостность базы (критично).**
   В отсутствие локальной SQLite нельзя подтвердить фактическое состояние 1131 товаров и 143907 строк на 22.11.2026. Проверить на компьютере, предварительно сделав копию; после анализа сравнить хеши защищённых таблиц и исторических строк.
8. **Ручная валидация и официальные документы (не выполнено).**
   83 ранее пройденных синтетических теста не доказывают точность сопоставления с реальными регистрационными документами. Не публиковать клиническую точность до независимой разметки.

## Что добавлено для P1/P2

- `scripts/validation_v047.py`: два режима `prepare` и `run`, согласованное резервное копирование SQLite через SQLite Backup API, две независимые копии (базовая и тестовая), SHA-256, `integrity_check` и `foreign_key_check`, сравнение содержимого защищённых таблиц и исторических строк, отдельный новый запуск, локальные JSON и CSV.
- `validate-v047-windows.ps1`: единый сценарий Windows, отдельное виртуальное окружение Python и тесты перед `prepare`.
- `tests/test_validation_v047.py`: синтетические проверки запрета запуска в рабочем репозитории, целостности снимка, отказа при нарушении внешних ключей, отказа от повторной перезаписи и защиты CSV от формул.
- Запрет на слияние и внедрение до завершения локальной и ручной проверки.
